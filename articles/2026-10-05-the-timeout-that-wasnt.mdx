# 一次并非超时的 AI 流式请求超时

生产环境里的 AI 请求连续失败，错误信息非常直接：等待流式响应的第一个数据块超时。

这看起来像一个常见问题。可能是模型服务响应慢，可能是网络不稳定，也可能是超时时间设得太短。可随着排查深入，我们发现：请求并没有真的“卡在服务端”，网络也没有慢到需要长时间等待。真正导致错误发生的是客户端读取响应体的那一步。

这次故障最有价值的地方，不只是最后修复了一个兼容问题，而是它展示了一个很容易被忽略的事实：**超时通常只是计时器最终观察到的结果，不一定是故障本身。**

## 从一个合理但错误的判断开始

生产日志显示，请求发出后很快就收到了模型服务返回的请求标识 `RequestId`。这意味着 DNS 解析、TCP 连接、TLS 握手和 HTTP 响应头至少已经走通了一部分。然而，响应体中的第一个 SSE 数据块迟迟没有到达，最终触发超时异常流程。

初看之下，最合理的解释仍然是模型服务没有及时生成内容。于是排查从最常见的方向开始：

- 检查 Web 与 AI Worker 是否运行正常，进程有没有发生异常重启或遇到资源耗尽。
- 检查生产服务器到模型服务的 DNS、TLS 和基础网络连通性。
- 对比本地与生产环境的端点、模型和请求参数。
- 使用最小请求排除上下文过大、工具调用和复杂业务数据的影响。
- 检查生产凭据是否失效、受限或绑定了不同的服务能力。

这些方向都合理，但是实际检查下来没有任何一个是真正导致问题出现的原因。

## 第一处转折：非流式请求是正常的

对同一个端点、同一模型和同一凭据发起非流式请求，响应在一秒左右正常完成。这至少说明：

- 凭据能够通过认证。
- 模型可用。
- 生产服务器能够访问服务端。
- 服务端可以正常生成结果。

问题开始从“模型服务整体不可用”收缩为“流式链路中的某一环异常”。

不过，生产环境配置了多个模型，而本地只配置了一个。一次早期诊断没有固定模型，存在选中不同模型的可能。修正这一方法问题后，我们强制使用本地已验证的模型再次测试，生产环境仍然卡在相同位置。

凭据配置、端点和模型的差异至此都被排除。

## 不再猜测，建立对照测试组

当高层配置看起来完全一致时，继续反复修改超时时间已经没有意义。我们改为在同一台生产服务器上，使用相同的端点、凭据、模型和最小测试请求，只替换 HTTP 客户端实现。

| 客户端路径 | 收到响应头 | 首个流式数据 | 完成请求 |
| --- | ---: | ---: | ---: |
| curl，HTTP/1.1 | 正常 | 约 0.6 秒 | 约 0.8 秒 |
| curl，HTTP/2 | 正常 | 约 0.5 秒 | 约 0.7 秒 |
| Bun 原生 `fetch` | 正常 | 约 0.5 秒 | 约 0.7 秒 |
| `undici.fetch` | 正常 | **持续等待** | **无法完成** |
| `undici.request` | 正常 | 约 1.0 秒 | 约 1.2 秒 |
| `undici.request` + 固定地址 Agent | 正常 | 约 0.4 秒 | 约 0.6 秒 |

这个对照测试让问题突然变得清晰：

1. 服务端确实在及时输出流式数据。
2. 生产网络没有阻止 SSE 数据传输。
3. HTTP 请求版本都不是决定因素。
4. 固定 DNS 解析结果的自定义 Agent 也不是问题来源。
5. 只有 `undici.fetch` 对应的响应体读取路径无法继续消费数据。

所谓“五分钟请求超时”，其实是响应头已经到达后，Web `ReadableStream` 读取一直没有返回。计时器只是在设定的五分钟后把这个停滞报告了出来。

## 为什么本地始终无法复现

本地测试一直正常，是这次排查最具迷惑性的部分。

本地和生产使用相同的应用代码、相同凭据和相同模型，但运行平台不同：本地是 macOS，生产是 Linux。相同版本的 Bun 和 Undici 在两套平台上的组合表现并不一致。

最终证据指向 Bun/Linux 环境中 `undici.fetch` 返回的 Web `ReadableStream` 读取路径。它能成功返回状态码和响应头，却在继续读取流式响应体时停滞。相同请求改走 `undici.request` 提供的响应流后立即恢复正常。

更准确地说，这是一个特定运行时、平台与客户端抽象组合产生的互操作问题，而不能简单归因于“Undici 不支持流式响应”或“Bun 的 fetch 有问题”。缩小结论的范围很重要，否则修复很容易变成另一个未经验证的猜测。

## 不能直接换成原生 fetch

既然 Bun 原生 `fetch` 工作正常，最简单的修改似乎是删掉 Undici，统一使用全局 `fetch`。但原实现使用 Undici 并不是偶然。

AnonResume 允许部署者及用户（如果启用了相应的选项）配置兼容 OpenAI 协议的模型端点。请求这些端点前，系统会解析并验证目标地址，再将连接固定到已经通过检查的 IP，同时保留 TLS 所需的原始主机名。这样可以降低 DNS 重绑定和服务端请求伪造带来的风险。

如果只为了恢复流式输出而改用一条不支持固定 Dispatcher 的请求路径，就会牺牲安全能力换取兼容性。这是绝不可行的。

最终方案是：

- 固定地址的直连请求从 `undici.fetch` 切换到 `undici.request`。
- 继续使用原有 `Agent`、固定 IP 和 TLS SNI 主机名。
- 保留每次重定向后的地址重新校验。
- 保留连接、首个数据块、空闲和总请求超时。
- 保留最大响应体限制，并在取消时主动销毁响应流。
- 为必须经可信代理的路径保留受控的 Fetch 实现。
- 在适配器内部把 Fetch 响应和 Undici 响应整合为统一读取接口，让 SSE 解析逻辑不依赖具体传输类型。

如此一来，我们替换的是有问题的流读取抽象，而不是绕过原有安全设计。

## 在部署之前回到生产环境验证

本地测试通过还不足以证明问题解决，因为故障本来就只在生产平台出现。

我们把修复后的适配器传输到同一台 Linux 服务器，用相同配置发起一次最小的流式请求。首个内容数据在不到一秒内到达，请求随后正常结束，并返回完成原因。

这一步同时回答了两个问题：

- 修改确实覆盖了生产环境中的异常路径。
- 原有 DNS 固定和 Agent 路径不会重新触发问题。

## 这次排查留下的经验

### 1. 超时阶段比超时时长更重要

“请求超时”提供的信息太少。连接前超时、等待响应头超时、等待首包超时、流式空闲超时和总时长超时对应完全不同的故障域。将超时拆成阶段，才可能知道下一步应该观察哪里。

### 2. 收到响应头不等于响应链路正常

许多监控逻辑将状态码到达视为上游正常可用，但对流式传输协议而言，响应头到达只是开始。客户端还必须持续、及时地消费响应体。首个数据包的到达时间和相邻数据块间隔应该被独立观测。

### 3. 相同代码与配置不代表相同运行时行为

运行时、操作系统、网络库以及 Web Stream 与 Node Stream 的适配层都可能改变行为。只在开发机上测试成功，不能排除生产平台特有的兼容问题。

## 结语

如果只看最终错误，这是一场持续数分钟的 AI 请求超时。如果看完整证据链，它实际上是一场在响应头之后发生的客户端流读取停滞。

问题之所以有趣，正是因为每一个早期判断都足够合理：生产网络、模型服务、密钥权限、模型差异和超时策略都有可能造成相似现象。真正推动排查前进的，不是更大胆的猜测，而是逐步让同一请求穿过不同传输路径，并观察它究竟停在哪里。

超时只是结果；找到最后一个已经成功完成的步骤，才是诊断的开始。
